# Maker colours come from one table

Status: accepted by the owner (D131 and D197; Set 1 as D211 on 2026-11-12). Superseded in part by D250 (2026-11-13): see the note below. Recorded here on 2026-11-13 because a later design pass re-derived the colours and contradicted Set 1.

> **Superseded in part by D250 (owner, 2026-11-13).** UI accents (`colour`: tabs, fader strips, record chips, chart series) are the old pastel palette, completed ("Old+"), not Set 1 (D211). Values and alternates are in `desktop/cockpit/README.md`. Rockets keep the website livery, and the one-table rule, fields and checks below still hold. The Set 1 values named below are kept as history.

## Context

Maker colours were picked several times by hand: in the website, in cockpit prototypes, and again in design passes that did not know the earlier decision. Each pass produced a different palette, and black-and-white brands (OpenAI, Z.ai, xAI, Cursor) ended up as near-white or grey marks that could not be told apart.

## Decision

- **One table.** `desktop/cockpit/src/livery-table.ts` is the only place app code reads a maker colour from, through `brandColour()` (UI accent) and `rocketColour()` (rocket livery) in `livery.ts`. Never pick, sample or re-derive a maker colour anywhere else.
- **Fields.**
  - `colour` is the UI accent: engine tabs, fader strips, record chips, the subscription header.
    - Coloured brands use their real brand colour (D131, D197), for example Claude `#d97757`.
    - Black-and-white brands used Set 1 (D211, superseded by D250 for UI accents): Codex/OpenAI `#10a37f`, GLM/Zhipu `#3859ff`, xAI `#f5e642`, Cursor `#f79dcb`.
  - `alt` is the collision shade. When two makers closer than the collision threshold share one view, the later one takes its `alt` (for example GLM next to Kimi, xAI next to OpenCode).
  - `rocket` is the website livery and is used only for anything that paints a rocket (launch-field scene, porthole stills). It never colours UI.
- **Colour is never the only signal.** Every coloured mark sits beside the maker's logo or name.
- **How the table is made.** `livery-table.ts` (and `desktop/app/livery.css`) are generated by `desktop/cockpit/sync-livery.mjs`. Its inputs are:
  - `livery-shared.json`, a verbatim copy of the website's shared maker table;
  - the app-only overrides in `sync-livery.mjs` (`APP_UI` for the UI accents, `TOOLS` for tool vendors with no maker row).

  Where the two differ, the generated table wins for UI. Since D250 they differ on purpose for every maker (before it, for OpenAI, Zhipu and xAI): the JSON keeps the website colour, which survives in the table only as `rocket`. To change a colour, edit the overrides or refresh the JSON, then run `node sync-livery.mjs`. Never hand-edit the generated files.
- **Checks.**
  - `node sync-livery.mjs --check` (part of the cockpit `npm run check` and `npm test`) fails when the generated files do not match their inputs. With `--source <file>` it also checks the JSON against the website's table.
  - `desktop/tests/cockpit/unit/livery.test.mjs` pins the D250 values (Set 1 until 2026-11-13), the collision shades, the contrast floors and the rocket/UI split.
  - `desktop/tests/cockpit/unit/maker-colour-source.test.mjs` fails when any cockpit source or native Swift file other than the table and its JSON copy hard-codes a maker colour as `#rrggbb` or `0xrrggbb`.

## Consequences

- A design or visual task takes maker colours from the table. If it believes a colour is wrong, it proposes the change against this ADR and the owner decides; it does not ship a new palette.
- Native code that needs maker colours gets them from the table, either through the cockpit bridge or from a file generated from it that is added to the check's allow-list.
- The table and the details behind each value (brand source, contrast, day-theme rule) are documented in `desktop/cockpit/README.md`.
