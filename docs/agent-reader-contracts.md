# D590 reader contracts: translation and upgrade gates

Companion to [the auto-detection design](agent-usage-auto-detection.md); direction approved, with coordinator corrections required before Step B. FEEDFIX owns the shared quota/bridge contracts and its M-reader files; the second reader lane owns the assigned S-provider and local-history files. CLIJIT consumes the additive DTOs/status codes and publication schema; App/client lanes render them. Research only: no real credentials, Keychain queries or authenticated provider calls.

## CodexBar 0.81.0 safety audit

Checked at **0.81.0 / `ee890b5f392e70d6e20162d3e95cf9f1be265b60`**. These are verified capabilities/paths, not a claim that every invocation takes all of them. None is compatible with silently admitting an entire provider registry as safe.

| Coordinator claim | Pinned verification | Admission consequence |
| --- | --- | --- |
| Gemini refreshes with extracted client secrets | [Gemini docs][SG] describe expiry-triggered Google OAuth refresh and extracting client ID/secret from the installed CLI; [probe source][SGP] implements token refresh and installation discovery. | No Gemini bridge admission; native reads only the current unexpired access token. |
| Gemini enumerates projects | The same docs/probe use `https://cloudresourcemanager.googleapis.com/v1/projects` when Code Assist discovery lacks a project. | Native may use `loadCodeAssist` + quota in one two-call read, never enumerate Cloud Resource Manager. |
| Claude delegates refresh | [Claude docs][SC] describe delegated `claude /status`; [coordinator source][SD] calls `ClaudeStatusProbe.touchOAuthAuthPath`, and recovery can cause the owner tool to write credentials. | No delegated refresh or automatic Claude bridge, even when OAuth mode is selected. |
| Provider CLIs are launched | Claude's pinned docs describe CLI/PTY `/usage` probes and Auto fallback to CLI; delegated refresh is another CLI path. Gemini installation discovery can also run node-manager commands. | Provider CLI launches are now allowed **only after audit proves a read-only, no-quota, no-refresh command**, including startup/error paths. Chat/session probes, opaque auth repair and unrelated discovery commands do not qualify. |
| Credentials are copied into CodexBar's Keychain | [Cache store][SKC] uses service **`com.steipete.codexbar.cache`**; [Claude credential store][SCC] calls its cache writer after credential reads. This is a credential cache, distinct from harmless sanitised quota snapshots. | Standard mode disables persistent Keychain caching. Advanced mode separately permits the explained provider session-cookie cache and scoped Forget cleanup; no tool OAuth credential copying/rotation is permitted. |
| Keychain uses Security.framework | [Security wrapper][SKS] calls `SecItemCopyMatching`, `SecItemAdd` and `SecItemUpdate`; [Claude strategy][SKR] defaults to `.securityFramework`. Its `/usr/bin/security` strategy is experimental and not a universal helper guarantee. | Our native reader must use `/usr/bin/security`. The owner explicitly permits the pinned CodexBar binary to use its own Keychain access under the applicable advanced grant. |

**Available controls, and their limits:** [CLI options][SOP] provide `--source api|oauth` to constrain strategy, but **no general `--no-refresh` or `--no-credential-cache` flag**. `--json-only` controls output; `--no-credits` is a presentation option, not an authentication safety control. `cache clear` mutates existing state and does not disable future caching. [KeychainAccessGate][SKG] recognises **`CODEXBAR_DISABLE_KEYCHAIN_ACCESS=1`** (also the app's `debugDisableKeychainAccess` preference); it gates Keychain access/cache persistence, but does not prohibit file-token refresh, in-memory credential caching, provider CLI launches or project enumeration. Test-only Keychain suppression is not a production safety contract. No combination of these controls establishes the required general read-only mode at this pin.

Therefore **automatic CodexBar fallback stays OFF for every head**. Long-tail routes follow the owner-approved access classes below. No class permits refresh or inference; standard requires the Keychain-disable flag, explicit browser-Off policy and no persistent credential caching; advanced browser reads require a separate provider grant and scoped Forget cleanup. Audited read-only, no-quota CLI launches and the explained advanced cookie cache are explicit owner exceptions to the previous blanket bans. Seed unaudited routes with `audited:false`, `pin:null`; “not yet supported” means no invocation. Translation fixtures do not establish runtime safety.

## CodexBar access classes — complete 0.81.0 inventory

Owner decision: [architecture section 4 at `0e1a422`][AC]. Inventory equals all **110** IDs in the pinned [generated registry list][RID]: **14 standard, 37 browser-session, 59 not-read**. The class describes the selected ModelPlan helper route at this pin, not every alternate mode CodexBar offers. Head-provider entries are `not-read` **through CodexBar** because native readers own them; this does not disable native reading. API-key-only/manual-secret integrations are not offered. Existing native readers, including Kimi, still take priority over any helper route.

| Access class | Consent, execution and storage contract |
| --- | --- |
| `standard` | Detected own local login/records or an audited read-only, no-quota CLI command; included in one-click consent. **Every invocation sets `CODEXBAR_DISABLE_KEYCHAIN_ACCESS=1` and explicitly sets `cookieSource: off` for every provider in the generated config.** Disable browser discovery/enrichment/fallback, including Safari/Gecko and raw localStorage paths. No token refresh or persistent credential copy/cache. A CLI mode label alone proves none of these properties. |
| `browser-session` | Advanced, **off by default**, excluded from one-click consent. Separate per-provider grant after the full explanation below. Only an existing selected browser sign-in; no OAuth refresh, login/repair or inference. CodexBar may use its own Keychain/Safe Storage access and session-cookie cache under that grant. |
| `not-read` | No helper invocation or connect offer. Refresh/login flows, API-key-only/manual-secret paths, native-owned heads and paths without a proved eligible mode remain “not yet supported.” Record the reason; a detected installation is not a grant. |

**Classification is not `audited:true`.** The table is a complete source-based access-policy port. Standard/browser rows identify the only candidate route, not a real-account pass or a completed call-graph/child-CLI audit. Every route must also pass the pin/platform/source audit, per-read request budget, identity/translation contract and beta rules before activation. Rows that cannot meet those constraints at 0.81.0 stay disabled even though their access class is known. Browser fallbacks/enrichment mentioned in a provider guide are **not** implicitly authorised by a standard classification. Counts differ from “about 50 web providers” because this table selects native ownership/local paths where applicable and rejects manual-secret-only paths.

Each row links the guide read at the exact pin. Mixed-mode decisions also checked the ClinePass, Kimi, Kilo, Amp, Codebuff, Nous, Muse, Zed, JetBrains, CodeRabbit, Alibaba Token Plan, Copilot, Grok, Cursor, HuggingFace and Augment descriptors at the same tag. The pinned Muse plugin posts the existing device token to `/muse-code/key`, reads returned quotas and **discards** the returned inference key; the standard candidate uses an already-inline CLI token with browser availability Off, not Keychain recovery or inference. Its audit must retain that exact projection and prohibit persistence of the returned key. Kiro's guide explicitly says its chat probes create sessions and may refresh auth, so the CLI relaxation does not admit it.

### Keychain flag verification and its limits

**Confirmed for persistent credentials and Chromium decryption at 0.81.0:** [`KeychainAccessGate.swift`][SKG] treats exactly `CODEXBAR_DISABLE_KEYCHAIN_ACCESS=1` as disabled and mirrors the gate to `BrowserCookieKeychainAccessGate`. [`KeychainCacheStore.swift`][SKC] makes `canUseRealKeychain` false, blocking persistent reads/writes to `com.steipete.codexbar.cache`. [`BrowserCookieImportOrder.swift`][BCI] rejects every candidate whose `usesKeychainForCookieDecryption` is true; on macOS this covers Chromium-family browsers. It does so before their cookie-source availability/decryption attempt.

Do not overstate the flag: Safari and Gecko/Firefox are explicitly exempt from that Chromium filter. **Firefox cookies are plaintext; Safari cookies are readable with Full Disk Access. Neither requires the blocked Keychain decryption step.** It does not ban raw browser localStorage, token refresh or provider subprocesses. The cache store can retain values in **process-local memory**: unbundled CLI processes use that store, and disabled persistent cookie access has a memory fallback. Thus “disables credential cache” means **disables persistent Keychain credential caching**, not erases all transient values or existing cache entries. Standard invocations require disposable bounded children, no secret-bearing config/log/output, and separately proved browser-Off/fixed-source policy.

**Mandatory generated-config invariant:** for standard mode, set **`cookieSource: off` on every provider**, not only the one requested by `--provider`. Only the selected **user-enabled `browser-session` provider** with a valid separate advanced grant gets **`cookieSource: auto`**; every other entry stays off. An advanced grant for provider A must not permit browser access during standard provider B's read. Start from an all-Off ModelPlan-owned config, never an ambient CodexBar config/default, and rebuild it for each class/consent/pin context. Config failure, a new provider lacking an enforceable Off path, or revocation is a no-launch result; never fall back to default cookie settings. The audited source must also honour Off for cached/manual cookie and browser-localStorage/enrichment paths.

For advanced mode, remove only ModelPlan's injected standard-only restriction after that provider's separate grant; preserve any user-imposed disable, privacy veto and recorded denial. A stable pinned CodexBar may make its own Keychain calls. The `/usr/bin/security` requirement applies to **ModelPlan's native readers only**, not to CodexBar internals.

### Advanced consent, detection and Forget readings

First-run groups standard tools (pre-checked) separately from browser-session candidates (unchecked, advanced). The one-click **Allow selected standard tools** action never grants browser access. An advanced checkbox opens its own provider-specific explanation and confirmation; it is not added to the one-click submission. Web-only providers with no safe local signal use **Add subscription**. Detection never opens, enumerates or stats browser cookie/localStorage/profile/history data to determine provider presence; an installed browser alone is no tool/provider signal.

Per-provider text: **“Allow CodexBar to read your existing <provider> browser sign-in and send its session credential to <provider> to read usage. macOS may ask for your browser's ‘Safe Storage’ key; that key can unlock the browser's saved sign-ins. CodexBar reads the selected provider's session and may keep its cookie in its own cache (`com.steipete.codexbar.cache` when persistent Keychain caching is available; otherwise process memory). Nothing is sent to ModelPlan. This is optional; Forget readings also clears CodexBar's cookie cache for this provider.”** The prompt is genuine; do not claim provider-only scope for the Safe Storage key or hide/bypass Deny. No repeated prompt without explicit Settings Retry. Existing browser-session consent cannot be inferred from standard consent, a catalogue switch or an upgrade.

Forget readings first revokes/cancels that provider and waits for its child to exit, then purges ModelPlan readings and runs the verified pin's **`codexbar cache clear --cookies --provider <id>`**, using the canonical registry ID, fixed arguments and the **same cache/bundle context**. [`CLICacheCommand.swift`][CCC] calls `CookieHeaderCache.clearAllScopesDetailed(provider:)`, including that provider's scoped cookie entries. Never use `--all`, clear another provider, delete browser cookies, or touch tool-owned credentials. Each source switch also ends the old disposable child, dropping its transient memory cache.

The unbundled 0.81.0 CLI caches in memory, so a newly spawned clear command cannot erase another live child's memory or a different bundled app's Keychain context. Cancellation/child exit handles its memory; do not report an unrelated bundled cache cleared. If the publication distributes a bundled helper that persists cookies, the clear command must address that exact verified bundle/cache. Keep cleanup pending and return a safe failure if that cannot be proved or clearing fails; local readings stay forgotten, background reads remain revoked, and no secret/error body is exposed. CLIJIT owns per-provider consent/revocation/pending-cleanup records; FEEDFIX owns child cancellation and the scoped helper clear operation; App owns explanations and Retry UI.

Acceptance fixtures cover all 110 IDs/classes; **all providers explicitly Off in a generated standard config**, including synthetic readable Firefox/Safari stores; the flag alone not blocking those stores; only the selected separately granted advanced provider Auto; other granted advanced providers remaining Off; advanced-to-standard transitions; config failure/default-inheritance rejection; new-provider Off enforcement; advanced exclusion from one-click grants; honest Safe Storage wording; persistent Deny; scoped cache clear success/failure/context; cancellation/write races; no browser-data detection; forbidden refresh/inference; and CLI-command read-only evidence. No real browser store, credential, Keychain or vendor account is used.

## Every-provider daily contract gate

Extend `TestLiveCodexBarContract`, `scripts/pin-codexbar.mjs` and the **daily** `codexbar-pin` monitor. Use the actual verified candidate binary only for an audited safe unauthenticated JSON-envelope/error smoke path; never import host credentials, invoke login or perform inference. Store artifacts by version/hash; do not remove an older verified binary still referenced by any provider or rollback state. Enforce `minCli` for the audit/override-aware router so older copies cannot silently use the new default for a held provider.

Hypothetical admitted long-tail example: candidate B passes provider P but fails Q → default B, Q override A with its matching prior audit; only Q reports its held upgrade. This does not declare any current path safe or permit head fallback. A new provider with no passing A remains “not supported yet,” not routed to a random fallback. A bad archive/checksum/registry-integrity result blocks all uses of that unverified artifact/platform; a provider-specific contract failure does **not** block unrelated passing providers. The daily job always collects individual results and opens one reviewed pin/catalogue proposal including holds; it must not abort the entire proposal at the first provider failure or hide failures under a green aggregate label.
