# U6 Dock/menu Drive

Use the shared native-verification Launch, Doctor, guardian, Cleanup and Evidence helpers; this is an additional scenario, not a replacement runner. The subject is the ordinary ModelPlanCommunityApp route, never the U11a cockpit test host or the legacy probe executable.

## Prepare before the lease

1. Pin the source commit, test candidate binary/package hash and ordinary bundled engine hash. The candidate must contain the rows-backed normal entry. Synthetic HOME/TMPDIR contain no owner account, credential or Keychain data. Reuse the approved structural profile builder; do not copy a real profile or add a competing generator.
2. Allocate a new approved exchange batch under `/mnt/shared/modelplan/handoffs/20261030-u6/`, with an independent run/epoch subdirectory, README and file list. If the approved directory is absent or any write is refused, stop without a fallback location. Do not overwrite a prior batch.
3. Retain the exact start announcement on the unit's private task, matching GUI release/lease, absolute expiry of at most 1200 seconds, independent watchdog and stop-hook paths. The run's deadline includes launch, waits, action delivery and cleanup. No automatic renewal or retry.
4. Use shared `launch.py` to validate the existing run contract. Its execute route requires the matching release, fresh guardian heartbeat, exact executable hash and synthetic profile. A validation/dry run is not an App launch or Drive result.

## Drive

1. Announce window start on the authoritative unit task before launch. Stop on owner takeover or any guardian/lease/deadline failure. Do not repeatedly reclaim foreground activation.
2. Launch the actual candidate through shared Launch. Record owned process identity and separate active/key/visible/native-panel observations; a non-key Dock panel must not be misreported as a key-window failure. The App may request foreground activation once if the granted contract requires it.
3. Deliver real input to reveal the Dock. Capture only the owned candidate surface. Observe at least one current reading or explicit engine-provided reason; no value is invented for an empty synthetic profile.
4. Open the actual system status-item menu, capture its reading/reason text and deliver Refresh once. Record the delivered input and visible resulting state. An unchanged empty state is not proof of a remote refresh or provider freshness. Lack of a menu input capability is unsupported, never pass.
5. Quit the owned candidate. Shared Cleanup verifies only registered owned process identities, releases this run's lease/resources and removes only approved synthetic scratch. Announce window end + cleaned only after the real closure receipts exist. Retain evidence according to the batch policy.

## Evidence

New `bin/evidence-u6.py` derives bounded scenario outcomes from explicit receipts and delegates file hashing/manifest generation to the unchanged shared `evidence.py`. Keep screenshots, action receipts, source/package/profile bindings and cleanup in the same batch. Do not upload raw engine frames, account identifiers, paths, tokens or host metadata. Missing receipts remain not-run; unavailable capabilities remain unsupported. This scenario alone cannot establish owner freshness, official appearance or L2/L3 acceptance.
